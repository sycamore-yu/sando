\[

\rightarrow
椭球凸分解
\rightarrow
时空走廊

当前采集代码在已经拥有这份真实 `base_map（走廊分解实际输入地图）` 的位置，把 `visible_map（可见地图）` 写成了空值。

# 6. 关键问题三：当前动态障碍快照可能取错时间

对动态多时间重建，使用场景初始位置作为当前障碍位置会产生错误走廊。

# 9. 关键问题六：单时间模式当前可能只使用约三分之一求解线程

当前构造函数加载时间网络后，仍先设置：

```text
3个时间占位
3个求解器
每个求解器线程数 ≈ 总核心数 / 3
```

`schema 2（模式版本2）` 在真实请求中随后只产生1个时间。

因此正常单时间主链可能仍使用按3路并行预算分配的求解器线程。

这会影响：

- 单时间实际延迟
- 阶段6性能归因
- 与原系统的公平比较

时间网络预测失败时，当前代码会恢复原三个名义时间：

```text
1
sqrt(5)
5
```

所以不能简单把全部求解器永久减为1个。

推荐解决方法：

保留足够的回退求解器容量，同时让当前实际激活的时间数量决定线程预算。

实现前检查 `setGurobiThreads（设置求解线程数）` 对已初始化求解器的真实生效方式。

推荐验收：

- `schema 1（模式版本1）` 正常请求：3个活动时间，线程预算按3路
- `schema 2（模式版本2）` 正常请求：1个活动时间，主求解器获得单路预算
- `schema 2（模式版本2）` 时间预测失败：恢复3个活动时间，线程预算重新按3路
- 求解器数量、活动求解器数量、每个求解器线程数写入诊断指标
- 数学结果保持一致
- 正式阶段6测量前完成

不要为了性能删除原三时间回退。

# 10. 关键问题七：阶段6的0毫秒可能表示“没有这个事件”

当前：

- 找到首个赢家后才写 `usable_ms（首个可用结果边界时间）`
- 没有赢家时它保持 `0`
- 某些提前失败路径下 `reclaim_ms（资源回收完成边界时间）` 也可能保持 `0`

正式统计把这些0当作真实时间会产生错误。

必须在阶段6正式测量前处理。

建议输出空值表示没有出现对应边界。

可采用：

- `std::optional<double>`（可选双精度数）
- 或明确的有效标志

分析器必须区分：

```text
0毫秒真实测量
字段不可用
规划失败
局部规划未进入
```

当前边界语义保持：

`usable_ms（首个可用结果边界时间）`、`reclaim_ms（资源回收完成边界时间）`、`publish_ms（轨迹发布边界时间）` 都是从本次重规划入口开始的累计边界时间。

分析时再计算阶段差：

\[
reclaim\_after\_usable = reclaim\_ms-usable\_ms
\]

\[
publish\_after\_total = publish\_ms-total\_ms
\]

同时保留已有 `cancel_drain_ms（取消并等待其他求解器退出的时间）`。
